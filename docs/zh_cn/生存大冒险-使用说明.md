# 生存大冒险 自动答题 — 使用说明

> 面向《造梦西游4》「生存大冒险」答题玩法的 MaaFramework 项目。
> 题库由攻略表转录（`assets/data/adventure.json`），决策逻辑在 Agent（Python）里。

## 1. 它怎么工作

```
截图 → ①识别当前是哪个事件 → ②读左侧六维属性 → ③查题库算最优选项 → ④点击那一行
```

**① 事件识别（两级，先精确后兜底）**

| 方式 | 依据 | 说明 |
| --- | --- | --- |
| 题干关键词 | `adventure_ui.json` → `events.*.match` 里的正则 | 精确，需要为每个事件登记关键词 |
| 4 行选项文本 | 与题库选项简称做相似度匹配 | 兜底，**实测区分度很高**：危险任务 0.77，第二名仅 0.06 |

> 选项文本匹配之所以可行，是因为界面上 4 个选项的顺序与攻略表完全一致（已用「危险任务」验证），
> 所以可以逐行配对比较。若某种事件的匹配度过低（低于 `OPTION_MATCH_THRESHOLD = 0.55`），本项目按"未知事件"处理。

> **两个坑（v1.4 已修，登记新事件时务必避开）**
>
> 1. **关键词不能太宽。** 匹配是「按命中数打分、取最高分」，只要有一条模糊的宽模式命中，
>    它就会盖过本该命中的那个事件。曾经「危险任务」的关键词里有一个光秃秃的 `"族长"`，
>    于是「冒险前，族长准备送你一件礼物」也被判成危险任务（该局第 1 题按阶段 5 估值，实测平均掉 0.24 分）。
>    关键词要写到能唯一区分题干的长度，例如 `"很危险的任"`。
> 2. **每个阶段的事件都要登记齐全。** 只有 `events` 里登记了的事件才会先被题干匹配到；
>    没登记的只能走选项文本兜底，容易被上面的宽模式抢走。阶段 1 的四个事件
>    （冒险前神秘礼物 / 冒险前没好武器 / 危险任务 / 商品买卖必备）现已全部登记。

**② 决策规则（精确后向归纳，失败时退回启发式）**

- 选项的「成功要求」是**属性硬门槛**：当前属性 ≥ 全部门槛 → 必定成功，否则必定失败。
  表格中要求列为空的选项（如「开挂」「碰瓷」）判定为**必定失败**（`always_fail`）。

线上默认走**精确后向归纳**（`agent/adventure_logic.py` 的「精确后向归纳」一节）：
一局只有 10 题、每阶段的事件是已知的有限集合，于是整局等价于一个 10 步的马尔可夫决策过程，
用动态规划从第 10 题往前算出每个（题号, 六维）状态的最优期望分，再据此选选项。
**它比启发式多 1.05 分**（真实 7 个角色等权分布、4 个独立题序池配对比较，t=+32）。

- **题号由事件反推，不数决策次数**：精确后向归纳对「当前是第几题」极度敏感，
  而同一题可能被重复识别、重复决策（日志实测每局平均多出 1.55 条决策，最多 5 条）。
  早期版本用「决策计数」当题号，多读一次就把后续所有题都推迟一个阶段（实测每局掉约 0.10 分）。
  现在改为按事件所属阶段反推：同一阶段里，第 1 个不同事件算第 1 题、第 2 个算第 2 题，
  **同一个事件再次出现时题号不变**（见 `adventure_logic.question_for_event`）。
- **首题只在「第一次遇到这个角色」时停顿 10~20 秒**：归纳表在这一刻当场构建
  （单角色 30~59 万状态），建好后整表常驻，同一角色的后续每一局都直接命中缓存。
  一个会话最多只有 7 次这样的停顿（7 个角色各一次），之后全是零等待。
  流水线里 `生存大冒险_读题` 的 `timeout` 因此设为 90000；
  日志会打印「复用上一局留下的归纳表：N 状态」「开局：角色=X｜第 1 题=Y｜初值=…」
  和「本局策略：精确后向归纳（拉表耗时 X 秒，归纳表 N 状态…）」。
- 归纳表只是**题库的函数**（与角色无关），而且**整表常驻、不再按局清空**：
  单个角色的可达状态约 30~59 万，7 个角色的并集实测 **1,121,191** 条，上限 `EXACT_MAX_STATES`
  取 180 万正好装下，于是**每个角色只付一次建表钱**，之后不管随机抽到谁都命中缓存、
  首题零等待（内存代价约 150 MB）。真到上限时在**半数处裁剪**——表是纯缓存，
  丢条目只会重算，不会把精确策略关掉。
- **为什么值得常驻**（`python tools/measure_table_warm.py 14` 实测，7 个角色各出现两次）：
  旧策略「累计超过 40 万就清表」几乎等于每局重建，14 局白等 **192.6 秒**（平均每局 13.8 秒）；
  整表常驻后同样 14 局只花 **56.0 秒**，而且从第 8 局起是 **0.00 秒**。
  一个任务里打的局数越多，省得越多。
- 归纳不可用时**安静退回启发式**：在"能成功"的选项里选属性收益最高的；若四项全都会失败，
  选损失最小的。血量（健康）归零等于冒险结束，所以健康权重最高
  （见 `adventure_logic.py` 的 `DEFAULT_WEIGHTS`）。

## 2. 安装依赖

**不需要装任何东西。** Python 解释器和依赖（`maafw` / `numpy` / `strenum`）都在仓库自带的
`runtimes\python\` 里（156 MB），`interface.json` 的 `child_exec` 直接指向
`runtimes\python\python.exe`，用的是本目录的运行时、不读系统环境变量，
所以换机器、重装系统、系统 Python 被卸载都不影响。

自检（确认运行时完好）：

```powershell
runtimes\python\python.exe tools\runtime_check.py
```

输出「结论：全部通过」就是好的。如果 `runtimes\python\` 被清理工具扫掉了，
日志里会表现为「MAA 启动后 agent 连不上」、连 Python 报错都没有。这时重建：

```powershell
python tools\setup_runtime.py
```

它会从本机 Python 3.12 重新整理一份（本机没装 Python 3.12 的话，先装一次，或者从别的电脑拷
`runtimes\python\` 整个目录过来）。重建前请确认系统 Python 里能 `import maa`：

```powershell
py -3.12 -m pip install maa
```

> 运行时目录不进 git（体积原因），只在本地和发布包里。所以从 git 克隆出来的仓库需要执行
> 一次 `setup_runtime.py`，或者直接用发布包。

## 3. 使用流程

**第 1 步：手动进入答题界面**
先用现有任务「进入游戏」进入游戏，并打开「生存大冒险」，停在能看到题干和 4 个选项的界面。

**第 2 步（首次使用）：界面标定**
运行任务「**生存大冒险·界面标定（只截图）**」，它会在 `debug\screencap\` 下保存一张 MaaFW 视角的截图（1147×720）。
把这张图发给作者，用于校准 `adventure_ui.json` 与 pipeline 里的识别区域（ROI）。

> 为什么必须校准：现有 ROI 是按窗口截图（1412×933，含标题栏）按 ×0.8123 换算的估值，
> 未校准前 OCR 很可能读不到内容，任务会在 15 秒后自行结束（这是设计好的安全行为）。

**第 3 步：运行自动答题**
运行任务「**生存大冒险·自动答题**」，**不需要任何配置**——角色随机出现也不影响，
本项目第 1 题会先用左侧木牌上的**角色名**锁死初始六维，之后每题都从界面左侧识别六维属性（见 4.2）。

> **第 1 题只在「第一次遇到这个角色」时停顿 10~20 秒**（构建精确后向归纳的期望表）；
> 建好后整表常驻，同一角色后续每局秒回，别的角色最多再各付一次（7 个角色）。
> 看到卡住别以为死了，日志里会打印「开局：角色=X｜第 1 题=Y｜初值=…」
> 和「本局策略：精确后向归纳（拉表耗时 X 秒，归纳表 N 状态…）」。

日志在 `debug\adventure\adventure.log`，每题都会记录：识别到的事件、当前属性、选了第几项、理由。

**第 4 步：遇到未知事件**
题库里还没登记、且选项匹配度不足的事件，本项目会：记录题干与 4 行选项文本到
`debug\adventure\collected.jsonl`，存一张截图，然后**先点第 1 项**继续推进（采集阶段会牺牲这一题）。
把 jsonl 发我，即可批量补全识别特征。

## 4.1 抗坐标偏移设计

识别区域有两层保障，即使换算有偏差、或换了分辨率/DPI，本项目也能工作：

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 固定 ROI | `生存大冒险.json` 各 OCR 节点 | 720p 基准下写死的坐标 |
| 自适应定位 | Agent 的 `_locate_question()` | 运行时扫描黄色题干行，用实测区域覆盖固定 ROI |

两者已交叉验证：在模拟 720p 图上，自适应定位得到 `[336, 232, 674, 67]`，pipeline 里写死的是 `[335, 232, 680, 66]`，误差不超过 6 像素。

自适应定位只要求"能用 `[y][x]` 索引取到 BGR"的对象，因此不依赖 numpy，也能在离线测试里用
`debug/_sim_720p.raw`（一张模拟 720p 图的原始像素）验证。该文件缺失时场景 6 会自动跳过。

## 4.2 属性识别：不需要手填

角色是随机出现的，初始六维各不相同，所以本项目**不依赖任何手填数值**，每题都从左侧
「生存属性」面板直接 OCR。

**开局（第 1 题）会先认角色，用它把初始六维钉死。** 左侧木牌第一行就是角色名
（小沙 / 小吒 / 小猪 / 小唐 / 小玉 / 小猴 / 小白），7 个角色的初始六维已内置在
`adventure_logic.CHARACTERS`。第 1 题时属性还没被任何选项改过，所以那一刻面板上必然是
角色的初始六维——两者互为校验：

| 情况 | 处理 |
| --- | --- |
| 属性 OCR 全失败（账本也空） | **直接用角色初值** —— 这是主要的修复点；原先会退化成「所有门槛都不满足」，整局的价值基线全错 |
| OCR 与角色完全一致 | 不干预，记一行日志 |
| 只差一个属性 | 判为 OCR 读错一位，按角色纠正 |
| 差两处以上 | 判为「中途接手一局」，信任 OCR，只记录不一致 |

> 判据为什么可靠：题号 0 只可能是本局第 1 题；中途接手时遇到的第一个事件属于别的阶段，
> 题号不会是 0。所以「第 1 题」这个条件本身就能证明面板上是初始值。

第 2 题起的属性变化仍按下面三级兜底：

| 级别 | 方式 | 说明 |
| --- | --- | --- |
| 1 | 运行时自适应行定位 + 逐行 OCR | 自己扫描白色数字行的位置，最稳 |
| 2 | pipeline 里写死的 6 个 ROI + 逐行 OCR | 兜底 |
| 3 | 一次 OCR 整个数值列，按出现顺序取 6 个数字 | 逐行都失败时使用 |

三级全失败才回退「上一题的账本」；若账本也是空的（例如中途接手且第一眼就读不到），
则按「所有选项都不满足门槛」**保守处理**——选损失最小的那一项，宁可少赚也不会误判成功。

## 4.3 改完 assets 必须同步到运行副本（重要）

本项目其实有**两套**配置，内容并不相同：

| 位置 | 作用 |
| --- | --- |
| `assets/interface.json` + `assets/resource/` | 规范目录（入库、CI 打包用，任务较少） |
| 根目录 `interface.json` + `resource/` | **实际运行时被读取的副本**（含自行添加的任务） |

直接双击 exe 运行时，MFAAvalonia 读的是**根目录**那份。所以只改 `assets/` 不会生效，
必须同步一次：

```powershell
runtimes\python\python.exe tools\sync_to_runtime.py
```

同步规则：

- **生存大冒险\* 任务**：以 `assets/` 为准**整体替换**——新增、修改、删除都能同步过去
- **你自己的其他任务**：原样保留，不会被改动
- **选项**：新增的追加；已从 assets 删掉的（例如早期的「初始属性」）会一并移除
- 同步前备份成 `interface.json.bak`，可重复执行

> 注意：MFAAvalonia 运行时会把内存状态写回 `config\instances\default.json`，
> 所以**改配置时请先关掉程序**，否则改动可能被覆盖。那边残留的旧选项值也已清理过一次。

## 5. 怎么补充事件特征

在 `adventure_ui.json` 的 `events` 里加一条即可（题干关键词可选，加不加都能靠选项文本匹配）：

```jsonc
"玄武门": {
  "match": ["玄武门"],                                   // 题干关键词，正则
  "option_hints": ["仔细观察", "刻字", "合影", "走过"]     // 仅作备注
}
```

## 6. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 任务刚跑就结束 | 说明题干区域 OCR 没读到字 → ROI 不准，先做第 2 步标定 |
| 日志里全是"未知事件" | 选项 ROI 不准或 OCR 读串行；也可能是新事件，按第 4 步采集 |
| 点了错误选项 | 大概率是事件匹配错了（多个事件选项措辞相近），把日志发我调阈值 |
| Agent 没启动 | `runtimes\python\` 被清理工具扫掉了 → 跑 `python tools\setup_runtime.py` 重建，或见下面 6.2 |
| 属性读出来是错的 | 属性行 ROI 偏了；本项目在用 OCR 值之前会用输入项兜底，可在日志里看到「属性 OCR 不完整」 |
| 双击 exe 弹「无法验证发布者 / 安全警告」 | 见下面 6.1 |

### 6.2 `runtimes\python\` 被清理后的表现

`runtimes\python\` 是本地整理出来的目录（156 MB，不进 git）。**不会**被 MAA 自带的
更新/清理删除，只有系统级清理工具（手动的磁盘清理、某些"优化"软件、或整目录覆盖式更新）
才会动它。丢了以后的表现很特别：

- 日志里**没有**任何 Python 报错，也**没有** `adventure.log`
- MAA 界面表现为「任务启动后立刻结束」或「Agent 启动失败」
- `debug\maafw.log` 里能看到拉起 `runtimes\python\python.exe` 失败

处理：跑一次 `runtimes\python\python.exe tools\runtime_check.py`（会直接报哪一项缺），
再跑 `python tools\setup_runtime.py` 重建。

### 6.1 Windows 拦截程序启动的处理顺序

按顺序做，通常第 1、2 步就够：

1. **清掉下载标记**（文件是从网络压缩包解压出来时才会有）：

    ```powershell
    Get-ChildItem -Recurse | Unblock-File
    ```

2. **放开 Internet 区域的启动限制**：

    ```powershell
    Set-ItemProperty -Path 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings\Zones\3' -Name 1806 -Value 0 -Type DWord -Force
    ```

3. **给 exe 做本地自签名**（针对提示「此文件没有包含有效的数字签名」）：

    ```powershell
    powershell -ExecutionPolicy Bypass -File tools\sign_exe.ps1
    ```

    执行时 Windows 可能弹一次证书信任确认框，需要点「是」，否则签名不会被信任。

> [!WARNING]
> **不要**用关闭 SmartScreen「检查应用和文件」的办法来绕过。实测那样做只会让 Windows
> 退回更老的判定路径，弹出一个「未知发布者」对话框，问题并没有消失，反而更难判断。

### 6.2 连接窗口时发生错误

`debug\maafw.log` 里出现下面任意一行，说明是**截图方式全部失败**导致控制器初始化失败：

```text
cannot find any method to screencap!
failed to select screencap method
```

排查步骤：

1. 打开 `config\instances\default.json`，查看 `Win32ControlScreenCapType` 的值。
   只配一种方式时最容易崩——那种方式失败后没有任何备选。
2. 按兼容性依次尝试：`ScreenDC` → `DXGI_DesktopDup_Window` → `PrintWindow` → `FramePool`

    | 方式 | 要求 | 说明 |
    | --- | --- | --- |
    | `ScreenDC` | 窗口可见、未被遮挡 | 兼容性最高，直接读屏幕像素 |
    | `DXGI_DesktopDup_Window` | 窗口可见、未被遮挡 | 桌面复制后裁剪 |
    | `PrintWindow` | 可后台 | 窗口被遮挡也行，但游戏可能返回黑图 |
    | `FramePool` | 可后台、最快 | 依赖 Windows 图形捕获；对带防截图属性的窗口会返回 `E_ACCESSDENIED(0x80070005)` |

3. 想知道具体是哪种方式失败、失败原因码，在 `debug\maafw.log` 里搜 `screencap` 或 `speed_test`。

> 造梦盒子的窗口类名是 `ApolloRuntimeContentWindow`。这类内嵌运行时窗口常带防截图属性，
> `FramePool` 容易被拒，所以默认建议用 `ScreenDC`。

### 6.3 Agent 启动失败

MFAAvalonia 日志里出现下面这种，说明**创建 Agent 通信端时原生库就崩了**，
此时还没轮到启动 Python（与 Python、MaaFw、项目路径都无关）：

```text
启动 Agent 失败：Agent 'py' failed to start：External component has thrown an exception.
   at MaaFramework.Binding.Interop.Native.MaaAgentClient.MaaAgentClientCreateV2(IntPtr identifier)
   ---> System.Runtime.InteropServices.SEHException (0x80004005)
```

原因分两个层面：

1. **版本必须匹配（官方说明）**：MaaFW 自 **v5.5.0 起改变了 IPC 地址**，用 Agent 时
   「**client 和 server 必须一起升级**，不然连接不上」，表现就是
   `MaaAgentClientCreateV2` 抛 `SEHException`。
   本项目三处版本并不一致：C# 绑定 5.10.0、原生库约 5.12.2、Python 包 5.14.2。
2. 原生库缺少「IPC 可能失败则自动改用 TCP」的回退保护（后续版本才加入），
   AF_UNIX 初始化失败就直接抛异常。

按推荐顺序尝试：

1. **先把 Python 包降到与原生库同版本**（最快）：

    ```powershell
    py -m pip install MaaFw==5.12.2
    ```

2. **把项目移到纯英文路径**（例如 `C:\MaaTest\`）再运行——socket 路径可能受目录名影响。
3. **升级 MaaFW 原生库到 v5.14.2**（与 Python 包一致）：从
   [release](https://github.com/MaaXYZ/MaaFramework/releases) 下载 `MAA-win-x86_64-v5.14.2.zip`，
   解压后用其中的 `Maa*.dll` 覆盖 `runtimes\win-x64\native\` 下的同名文件（**先备份**）。
   注意 C# 绑定是 MFAAvalonia 自带的 5.10.0，跨版本兼容性无法保证。
4. 若以上都不可行，改成**纯 pipeline 方案**：用 OCR 读出属性数值，再用 `expected` 正则
   匹配数值区间（如 `[4-9]` 代表 ≥4）来模拟判断，节点数会大幅增加，但不再依赖 Agent。
